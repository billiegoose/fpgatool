# Amber / Flash Atlas

Read-only browser visualizer for the Basys 3 MFS1 user-flash filesystem. It uses
the RED2 font copied from `raster-engine/fonts/RED2-Regular.woff2` and Amber
Components' original palette: `#060200`, `#5b2400`, `#dd5800`, `#ff3400`.
All text is rendered uppercase with CSS because the current RED2 font has no
lowercase glyphs. Filenames, search values, and extracted bytes keep their
original case and contents.

From the repository root:

```sh
python3 -m http.server 8765 --bind 127.0.0.1 --directory tools/filesystem-visualizer
```

Open <http://127.0.0.1:8765/>. No installation or build is needed. The initial
image is an explicitly synthetic demo, generated by the real host writer.
Open or drop a binary dump to replace it. File contents remain in the browser;
there are no uploads, external fonts, or board connections.

Accepted images:

- Full 4 MiB flash: exactly 4,194,304 bytes. Configuration bytes are ignored.
- User partition: exactly 1,966,080 bytes, with byte zero corresponding to
  physical flash address `0x220000`.

The grid contains 30 64 KiB erasable sectors. Sectors 00–01 at
`0x220000..0x23ffff` preserve legacy assets; sector 02 at `0x240000` holds the
index; sectors 03–29 at `0x250000..0x3fffff` hold newly allocated blobs. These
addresses match `boards/basys3.toml`. Index references may point to either blob
region, but cannot overlap or cross the index sector.
Each blob appears in every sector it touches, with the bytes and
percentage belonging to that sector. Empty files appear at their recorded
address without occupying a page. Aliases sharing an address, length, and
content ID share one entry; all their names are listed. Click the entry to
inspect each index reference, its raw record, and a text preview, or extract
the original bytes. Click the index categories to inspect committed, corrupt,
or uncommitted slots. Search highlights matching blobs without moving them.

CSS Grid arranges sectors; vertical Flexbox arranges entries. A file's
preferred and maximum height is its percentage of the usable sector body,
subject to the minimum required for its labels. Entries can shrink to that
minimum; sectors scroll when labels cannot fit. These are readable lists,
not exact area charts. The bottom meters show actual 256-byte page occupancy,
counting deduplicated blobs and history once per physical page.

The decoder validates the exact six-byte MFS1 header, reserved header bytes,
commit marker, record CRC32, filename length/padding/UTF-8, and blob bounds.
Damaged records are isolated so later valid records remain visible. The latest
committed record wins for a name, including a deletion or interrupted status
update. Stored BLAKE2s-128 IDs are displayed but payload digests are not
recomputed. `0xfe` deletion status is recognized for inspection; the host does
not currently expose a delete command.

Formatting resets only the index sector; blob bytes remain programmed and become
unindexed. Unreferenced programmed pages are shown separately. Their owner cannot be
inferred safely from their contents. Erased pages are not necessarily reusable
by the append-only allocator, and this tool does not estimate reclaimable space.
It does not format, repair, upload, or read live hardware. The wire-format
reference remains [the filesystem docs](../../docs/mini-filesystem.md) and
`programming/mini_filesystem.py`.

Validate the parser (Node 18+ and Python 3):

```sh
node --test tools/filesystem-visualizer/filesystem.test.mjs
```

One test regenerates the fixture using `MiniFileSystem` and compares it with
the checked-in compact image. To refresh it after intentional format changes:

```sh
python3 tools/filesystem-visualizer/generate_demo.py
```

`demo.json` stores raw index records and runs of identical data bytes. The
browser reconstructs a byte-for-byte partition dump before parsing it; it uses
the same decoder as an opened binary file.
